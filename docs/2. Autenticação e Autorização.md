# Autenticação e Autorização

A autenticação da aplicação é baseada em **JSON Web Token (JWT)** e utiliza **cookies protegidos** para armazenar os tokens de autenticação.

## 1. Fluxo de Autenticação

O fluxo de autenticação é dividido nas seguintes etapas:

1. O usuário envia suas credenciais para o endpoint de **Login**.
2. A aplicação valida as credenciais informadas.
3. Após a autenticação, são gerados um **Access Token** e um **Refresh Token**.
4. Os tokens são armazenados em cookies protegidos.
5. Nas requisições seguintes, a aplicação recupera o **Access Token** armazenado no cookie.
6. O mecanismo de autenticação valida o token antes de permitir o acesso aos recursos protegidos.

---

## 2. Login

O processo de autenticação começa através do endpoint:

```http
POST /api/auth/login
```

O cliente envia as credenciais do usuário. A aplicação utiliza o sistema de identidade para verificar se o usuário existe e se a senha informada é válida.

### Requisição

```json
{
    "email": "string",
    "senha": "string"
}
```

Após a validação das credenciais, a aplicação gera os tokens de autenticação.

### 2.1. Bloqueio Temporário por Tentativas de Login

O sistema permite até **5 tentativas consecutivas de login malsucedidas**.

Ao atingir a **5ª tentativa malsucedida**, o usuário é **bloqueado temporariamente por 20 minutos**.

Durante esse período, novas tentativas de autenticação são impedidas, mesmo que o usuário informe a senha correta.

Após o período de bloqueio, o usuário poderá tentar realizar o login novamente.

## 3. Access Token

O **Access Token** é utilizado para autenticar as requisições realizadas pelo usuário.

Ele possui um tempo de validade limitado e contém informações utilizadas pela aplicação para identificar e autorizar o usuário.

O token é armazenado em um cookie com as seguintes propriedades:

- **`HttpOnly`**: impede que o cookie seja acessado diretamente por JavaScript no navegador.
- **`Secure`**: permite o envio do cookie somente através de uma conexão HTTPS.
- **`SameSite=None`**: permite o envio do cookie em requisições entre diferentes origens, quando utilizado em conjunto com `Secure`.
- **`Expires`**: define a data e o horário de expiração do cookie.

O cookie utilizado para armazenar o Access Token é:

```text
accessToken=<token>
```

---

## 4. Refresh Token

O **Refresh Token** é utilizado para obter uma nova autenticação quando o **Access Token** expira.

Assim como o Access Token, ele é armazenado em um cookie protegido com `HttpOnly`.

O Refresh Token possui um período de validade maior que o Access Token.

No projeto, o Refresh Token possui validade de **7 dias**.

O cookie utilizado para armazenar o Refresh Token é:

```text
refreshToken=<token>
```

---

## 5. Validação do JWT

Nas requisições autenticadas, a aplicação recupera o **Access Token** armazenado no cookie:

```text
Cookie: accessToken=<token>
```

O mecanismo de autenticação **JWT Bearer** utiliza o token para validar a requisição.

Durante esse processo, são realizadas as seguintes validações:

- **Emissor do token (`Issuer`)**;
- **Público do token (`Audience`)**;
- **Validade do token (`Lifetime`)**;
- **Assinatura do token (`Signing Key`)**.

Caso todas as validações sejam realizadas com sucesso, a requisição é considerada autenticada e o usuário poderá acessar os endpoints protegidos de acordo com suas permissões.

## 6. Recuperação de Senha

O processo de recuperação de senha utiliza o endpoint:

```http
POST /api/auth/forgot-password
```

Por meio desse endpoint, o usuário informa o **e-mail da conta cuja senha deseja alterar**.

### Requisição

```json
{
    "email": "string"
}
```

Para iniciar o processo, o e-mail precisa:

- existir no sistema;
- estar vinculado a uma conta;
- estar previamente confirmado na aplicação.

Após a validação, a aplicação gera um **token de recuperação de senha** e envia um link de recuperação para o e-mail informado.

Esse link contém uma **Callback URL** que permite ao usuário iniciar o processo de redefinição da senha.

### Redefinição da Senha

Após o usuário acessar o link recebido por e-mail, o endpoint de redefinição de senha é utilizado:

```http
POST /api/auth/reset-password
```

### Requisição

```json
{
    "email": "string",
    "token": "string",
    "newPassword": "string"
}
```

O campo `token` é preenchido automaticamente a partir do token recebido no link de recuperação.

Após a validação do token e das informações fornecidas, a nova senha é processada pelo sistema de identidade e armazenada no banco de dados em formato de **hash**, não sendo armazenada em texto puro.

---

## 7. Registro de Usuário

O registro de um novo usuário é realizado através do endpoint de cadastro da aplicação.

### Dados necessários

A requisição de registro recebe os seguintes parâmetros:

```json
{
    "email": "string",
    "password": "string",
    "phoneNumber": "string",
    "name": "string",
    "userName": "string"
}
```

### Política de Senha

A senha deve atender aos requisitos mínimos de complexidade definidos pela aplicação.

Ela deve conter:

- pelo menos **uma letra maiúscula**;
- pelo menos **uma letra minúscula**;
- pelo menos **um número**;
- pelo menos **um caractere especial**, como `$`.

### Exemplo de senha válida

```text
Senha082$
```

A senha não é armazenada diretamente no banco de dados. Após o cadastro, ela é processada pelo sistema de identidade e armazenada utilizando **hash de senha**.
